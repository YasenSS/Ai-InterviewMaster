## 1. 产品定位与核心流程

InterviewMaster 的核心不是让用户管理简历、JD、题集和任务等技术资源，而是让求职者用尽可能少的配置立即开始一场有针对性的 AI 模拟面试。

已确认的首版主流程：

1. 用户上传简历，系统在后台完成解析与事实提取。
2. 用户选择主要技术语言，例如 Java、Go、C++。
3. 首版岗位固定为后端开发；未来再扩展前端、客户端、Agent 开发等岗位。
4. 用户选择目标公司。
5. 后端根据简历、技术语言、岗位和目标公司生成题目大纲与内部题集合。
6. 题集不作为前端可管理资源暴露；用户点击“开始面试”后直接进入面试。
7. 面试模型节点结合题目大纲、当前进度和用户回答，选择追问、扩展问题或切换到下一个考察点。

核心产品原则：

- 用户创建和感知的是“一次面试”，不是“一份题集”。
- 题目大纲、题集合和追问分支属于面试编排的内部实现。
- 配置页只收集生成高质量面试所必需的信息。
- 开始操作应尽量接近即时；后台生成过程通过准备状态承接，不暴露任务中心和题集管理概念。

## 已确认的模块调整记录

### R-001 删除 JD／岗位描述模块

- 删除前端所有 JD／岗位描述相关的入口、导航、列表、详情、新建和编辑页面。
- 删除后端 JD／岗位描述相关接口。
- 后续改造时继续核对并清理与 JD 绑定的请求字段、服务逻辑、数据库关系和生成工作流输入。
- 首版岗位统一为“后端开发”，不再要求用户创建或选择 JD。

### R-002 增加面试记录

- 在前端“模拟面试”模块下增加“面试记录”入口和独立页面。
- 每条面试记录必须保存并展示一次面试的完整过程，而不只是摘要或最终分数。
- 完整过程至少包括：
  - 模型提出的全部问题，包括根据回答产生的扩展问题和追问；
  - 用户对每个问题的实际回答；
  - 每轮问题对应的评分；
  - 对用户回答的分析或评价；
  - 对应的参考答案／改进答案。
- 面试记录应能按一次完整面试回看，具体页面信息结构及其与现有“复盘报告”的关系留待后续讨论。

### R-003 题集改为后台内部产物

- 删除用户对题集的感知和独立管理流程。
- 前端不再提供题集导航、列表、详情、编辑、删除或重新生成页面。
- 用户点击“开始面试”后，由后端在后台生成题目大纲和内部题目集合，并自动进入面试。
- 模型节点根据题目大纲、当前面试进度和用户回答，决定扩展、追问或切换考察点。

## 2. 目标架构与用户旅程

```text
上传并解析简历
  → 选择主技术语言
  → 选择目标公司
  → 点击开始面试（岗位固定为后端开发）
  → 面试进入 preparing，后台生成蓝图与候选问题
  → 首题就绪后自动进入 active
  → 每次回答后决策：追问 / 切换考点 / 结束
  → completed 后异步评分
  → 在面试记录中回看完整问答与复盘
```

前端不展示题集 ID、异步任务 ID、JD 或生成资源管理流程。准备和报告生成状态均在当前业务页面中表达。

## 4. 面试编排与状态模型

面试状态：

```text
preparing ──生成成功──> active ──模型结束/用户结束──> completed
    └──────生成失败──> failed
```

动态轮次只保存已经真实提出的问题。后台候选问题不提前复制到前端，也不提前计入公开轮次。

每次回答后，面试官决策器只能选择：

- `follow_up`：围绕当前能力点继续深挖，并生成下一条具体问题；
- `next_capability`：从蓝图中选择下一个考点，由系统读取对应候选问题；
- `finish`：达到最小轮数且信息充分时结束面试。

追问受整场预算和单条问题链最大深度约束；模型输出无效、超时或越界时，系统安全降级到下一个考点，不能让面试卡死或无限循环。

## 5. 前后端改造方案

后端：

- 创建面试接口直接接收 `resume_id`、`primary_language` 和 `target_company`；
- 创建面试时同时创建内部蓝图载体与生成任务；
- 删除 JD 接口、数据关系与存储表；
- 删除公开题集接口，保留内部候选问题与证据关系；
- 真实面试轮次关联其内部来源问题，动态追问允许无来源问题；
- 报告按真实轮次评分，不能再用可变化的题号关联候选题。

前端：

- “开始面试”是唯一训练入口；
- `preparing` 页面自动轮询面试状态，成功后进入首题；
- 面试房间一次只显示当前已经提出的问题；
- “面试记录”提供历史列表和完整逐轮复盘；
- 删除 JD、题集和任务中心导航及页面。

## 6. 迁移与实现结果

本轮重构已经完成：

- API、OpenAPI 和前端生成客户端已移除 JD、公开题集及任务列表契约；单任务查询和重试仅供简历、面试准备、报告等业务页面内部使用。
- 创建面试会在同一数据库事务内创建内部候选题载体、`preparing` 面试和准备任务；后台只在首题就绪后激活面试。
- 每场面试固定 `resume_version_id`，出题、动态决策和评分始终使用同一份简历事实快照，保证历史记录可复现。
- 动态面试官只允许 `follow_up`、`next_capability`、`finish` 三种有界动作；单链追问深度、整场追问预算和最小结束轮数均由服务端约束。
- 回答采用当前轮次行锁和禁止覆盖规则；回答已保存但推进中断时，面试详情读取会触发确定性恢复，避免会话永久卡住。
- 准备和报告 Worker 增加任务认领、租户与资源关联校验、成功幂等、超时任务接管和失败状态补偿；业务页面支持原地重试。
- 面试记录列表支持服务端分页，完整记录逐轮展示问题、回答、分数、点评、参考答案和证据。

迁移 `00009_launch_redesign.sql` 会永久删除 JD 表。本次已在隔离的 PostgreSQL + pgvector 环境完成全量 `up → down → up`，并用带 JD、候选题和预创建轮次的 v8 样本验证：公司与简历版本正确回填，已展示轮次保留评分来源，未展示的未来轮次被删除。生产执行前仍须备份数据库；回滚只能恢复空的兼容表，不能恢复已删除的 JD 内容。
