## 1. Project Positioning

InterviewMaster is an AI interview-training platform for individual job seekers (monorepo).

Core loop: upload and analyze a resume → bind a target position/JD → generate personalized predicted questions → run a text-based mock interview → output scores and a review report. Beta capabilities include interview-experience intelligence retrieval and ASR speech transcription (`/api/v1/beta`). The MVP focuses on text-based mock interviews; M0–M3 and local Beta capabilities are complete.

Technical baseline: Go + go-zero REST, Asynq Worker, PostgreSQL 18 + pgvector, Redis, and S3-compatible object storage (MinIO); frontend: Next.js App Router + React + TypeScript + pnpm. The HTTP contract has `backend/api/interviewmaster.api` as its single source of truth and generates Go handlers, OpenAPI, and the TypeScript SDK.

Source: `README.md`.

## 2. Overall Architecture

Three application processes plus one infrastructure stack. The browser primarily communicates with Web; large files are uploaded directly to MinIO through presigned URLs.

```text
Browser
  │  REST (same-origin /api/v1 → Next rewrite)
  │  Presigned PUT → MinIO
  ▼
Next.js (web/) ──rewrite──► Go API (apps/api)
                              ├── PostgreSQL
                              ├── Redis (cache + Asynq enqueueing)
                              └── MinIO (signing/metadata)
                                    │
                         Asynq queue │
                                    ▼
                              Worker (apps/worker)
                              ├── Tika / Whisper (ASR)
                              └── Write back to PG / read MinIO
```

| Process | Entry point | Responsibilities |
| --- | --- | --- |
| API | `backend/apps/api/interviewmaster.go` | Configuration → `svc.ServiceContext` → `handler.RegisterHandlers` → `server.Start` |
| Worker | `backend/apps/worker/main.go` | Asynq: `resume:parse` / `object:cleanup` / `asr:transcribe` |
| Web | `web/src/app/` + `web/next.config.ts` | App Router; rewrites `/api/v1/*` to the API |

API dependency injection is defined in `backend/apps/api/internal/svc/servicecontext.go` (DB / Redis / ObjectStore / UploadSigner / TaskClient). Local infrastructure is defined in `docker-compose.yml` (postgres, redis, minio, tika; app/beta profiles).

There are three paths: synchronous REST; asynchronous tasks (API enqueue → Worker); and presigned direct uploads to object storage.

## 3. Directory Skeleton

### 3.1 End-to-End Main Flow

Main flow: register → upload resume (asynchronous parsing) → create JD → generate question set → create/answer interview → report.

```text
register/page → AuthForm → services.register → registerhandler/logic
resumes/new → ResumeUploadPage
  → createResumeUpload (presigned) → PUT MinIO → completeResumeUpload
  → resume_service Enqueue → Worker resumeparse (Tika + PG)
jobs/new → createJob → createjobdescriptionlogic
question-sets/new → createQuestionSet → createquestionsetlogic
interviews/new|/[id] → createInterview / answerInterview → interview logic
interviews/[id]/report → report → getinterviewreportlogic
```

Frontend aggregation point: `web/src/shared/api/services.ts`. Asynchronous branch: `resume_service.go` → Worker `resumeparse.go`.

### 3.2 Directory Structure

## 5. Available Capabilities

| Capability | Description | Implementation location |
| --- | --- | --- |
| Accounts and sessions | Register/login/refresh/logout, edit profile/change password | `auth/*`, `features/auth` |
| Workspace isolation | Users cannot see one another’s data | workspace API + DB |
| Resumes | Presigned upload → Tika parsing; CRUD/reparse | `resumes/*`, Worker `resumeparse`, `features/resumes` |
| JDs | CRUD + capability tags | `job-descriptions/*`, `features/jobs` |
| Question sets | Generate/list/edit/delete/regenerate (currently a fixed five-question stub) | `question-sets/*`, `features/question-sets` |
| Text interviews | Create session, answer/skip question by question, resume, completion lock | `interviews/*`, `features/interviews` |
| Reports | Overall + per-question review; reuse the report within a session | `getinterviewreportlogic`, `features/reports` |
| Asynchronous tasks | Status queries and retries | `tasks/*`, `features/tasks` |
| Dashboard / probes | Aggregated summary; health/ready | `dashboard` / `system` |
| Beta interview experience / ASR | Local fallback intelligence; Whisper transcription | `/beta/*`, Worker `asr` |

Boundary: question generation/scoring/interview intelligence are mostly stubs; the real external intelligence services are Tika and Whisper. See the historical [`acceptance-checklist.md`](acceptance-checklist.md) for comparison.

## 6. Difficult Parts

| Difficult part | Location | Why it is difficult |
| --- | --- | --- |
| Refresh-token rotation | `logic/auth/refreshlogic.go` | `FOR UPDATE` + new-session insertion + old-session revoke/replaced_by; concurrency and token-theft detection |
| Resume-upload pipeline | `logic/workspace/resume_service.go` | Presigned direct upload + server-side size/magic-byte validation + idempotent enqueueing; DB↔Asynq dual-write fallback |
| Interview state machine | `logic/workspace/createinterviewlogic.go` | `lockActiveInterview` row lock; answer/skip/complete/timing; unfinished-session confirmation |
| One report per interview | `logic/workspace/getinterviewreportlogic.go` | Lock session + completed state + generation in one transaction; `session_id UNIQUE` |
| Tenant isolation | `logic/workspace/helpers.go`, etc. | Every query carries `user_id`; omitting it creates an IDOR, so discipline is required |
| Task retries | `logic/workspace/gettasklogic.go` | Deduplicate and re-enqueue failed tasks; heavy/default queues |

Engineering value: session security, concurrent state machines, object storage plus asynchronous parsing, idempotent reports, dual-write consistency, and contract generation.
