# InterviewMaster 全流程开发大纲（go-zero + OceanBase + LangChainGo + Asynq）

> 状态：历史技术草稿，请勿作为当前开发基线。当前架构与选型以 [`技术方案_v1.md`](技术方案_v1.md) 为准。

> 目标：围绕三大核心能力——**面试记录深度复盘与批判**、**基于简历的精准押题**、**全网面经检索**——构建一套可扩展的 RAG 系统与 Go 微服务体系，兼顾隐私、安全、可观测与工程可维护性。

---

## Phase 0：项目基建与技术选型落地（1-3 天）

### 0.1 仓库与工程结构建议
- **仓库形态**：单仓多服务（monorepo），便于统一规范、共享 proto、共享基础库（pkg）。
- **目录建议**
  - `apps/`：各微服务（`user`, `resume`, `interview`, `search`, `rag`, `ingestion`, `gateway`）
  - `api/`：HTTP API 定义与网关配置
  - `rpc/`：各服务 proto
  - `pkg/`：公共库（OceanBase client、Embedding client、LLM client、鉴权、日志、追踪、错误码）
  - `deploy/`：k8s/compose/helm

### 0.2 基础能力清单（必须先打底）
- **统一身份认证**：JWT（用户态）+ Service-to-Service 鉴权（mTLS 或内部签名）。
- **可观测性**：结构化日志 + TraceId 贯穿（HTTP/RPC/Asynq）+ 指标（QPS/耗时/失败率/队列堆积）。
- **数据安全**：简历/面试记录加密存储（字段级/列级）+ 多租户隔离（Tenant/User 维度强约束）。
- **Prompt 与模型治理**：Prompt 版本化、参数（temperature/top_p）可配置、输出结构化（JSON Schema）。

## Phase 1：微服务拆分与接口契约（MVP 骨架，3-7 天）

### 1.1 微服务拆分建议（go-zero 适配）

#### 1) `gateway-api`（HTTP）
- **职责**：统一对外 REST/HTTP；鉴权、限流、聚合编排（轻量）；文件上传入口（简历/音频/文本）。
- **输出**：面向前端的稳定接口；内部调用走 RPC。

#### 2) `user-svc`（RPC）
- **职责**：用户、会员/额度、隐私设置（是否允许外部面经用于训练/召回）、API Key 绑定等。

#### 3) `resume-svc`（RPC）
- **职责**：简历上传、解析、结构化抽取（技术栈/项目/职责/亮点/空窗期）、版本管理、embedding 生成触发。
- **对外能力**：简历知识图谱化结果、简历考点权重。

#### 4) `interview-svc`（RPC）
- **职责**：面试场次（session）、问题-回答对（QA）、评分结果、批判报告、Golden Answer 生成与版本化。
- **对外能力**：复盘报告查询、对比报告（参考回答 vs 实际回答）。

#### 5) `search-svc`（RPC）
- **职责**：外部检索（Tavily/Firecrawl）、网页抓取与清洗、公司/岗位维度的面经素材入库。
- **对外能力**：按公司/岗位检索、素材更新。

#### 6) `rag-svc`（RPC，核心 AI 编排）
- **职责**：三条 RAG 链路的统一编排层（Resume 押题、Company 面经检索、Interview 批判优化）。
- **原则**：将“业务流程编排”与“数据入库/解析/检索细节”解耦；rag-svc 只组合、只决策。

#### 7) `ingestion-worker`（Asynq Worker，可与某个 svc 合并部署）
- **职责**：所有耗时任务（解析、embedding、面经抓取、长文本批判、ASR 转写等）。
- **原则**：与在线服务解耦，避免阻塞与资源争抢。

> 可选增强（正式版再拆）：`billing-svc`（额度计费）、`model-gateway`（多模型路由/降级）、`kb-svc`（更通用的知识库管理）。

### 1.2 API / RPC 契约（建议先做“最小闭环”）
- **简历**
  - `POST /v1/resumes` 上传 → 返回 `resume_id`
  - `POST /v1/resumes/{id}/analyze` 触发分析（异步）→ 返回 `task_id`
  - `GET /v1/resumes/{id}` 获取结构化结果与状态
- **押题**
  - `POST /v1/predictions`（resume_id + target_role/jd 可选）→ 返回问题集（可异步）
- **面经检索**
  - `POST /v1/company-intel/search`（company+role+keywords）→ 返回聚类与高频题（可异步刷新）
- **复盘**
  - `POST /v1/interviews` 创建 session（resume_id + jd）
  - `POST /v1/interviews/{id}/transcript` 上传文本/音频引用
  - `POST /v1/interviews/{id}/critique` 触发批判（异步）→ `task_id`
  - `GET /v1/interviews/{id}/report` 获取报告

## Phase 2：OceanBase 数据架构设计（关系 + 向量统一，5-10 天）

> 目标：一套数据模型同时支撑**业务元数据**（强一致、可查询、可审计）与**向量检索**（语义召回），并提供严格的多租户隔离。

### 2.1 关键设计原则
- **多租户隔离**：所有表必须带 `tenant_id`、`user_id`（或 `owner_id`）并建立联合索引。
- **文档-分块-向量三层**：Document（原文/清洗文）→ Chunk（可召回最小单元）→ Embedding（向量、模型版本）。
- **可回溯与可重算**：Embedding/Chunking/Prompt/模型版本都要可记录，便于重算与对比。
- **冷热分层**：在线检索走 chunk+embedding；原始大文本/音频引用只存引用与对象存储地址。

### 2.2 业务元数据表（建议）

#### 用户与项目域
- `im_user`：用户基础信息、额度、隐私开关
- `im_user_setting`：模型偏好、语言偏好、是否启用外部面经融合等

#### 简历域
- `im_resume`：简历主表（`resume_id`, `user_id`, `file_url`, `status`, `hash`, `created_at`）
- `im_resume_version`：版本化（同一简历多次更新）
- `im_resume_fact`：结构化事实（技术栈、项目、职责、指标）建议 JSON 存储 + 关键字段冗余索引

#### JD/岗位域（可选，但强烈建议）
- `im_job_desc`：`jd_id`, `company`, `role`, `content`, `created_at`

#### 面试域
- `im_interview_session`：`session_id`, `user_id`, `resume_id`, `jd_id`, `status`
- `im_interview_qa`：`qa_id`, `session_id`, `question`, `answer`, `order_no`
- `im_interview_report`：评分/批判/优化结果（结构化 JSON，含版本字段）

#### 面经域（公共素材库）
- `im_company_source`：来源（站点/URL/抓取时间/可用性）
- `im_company_doc`：面经文档级元信息（company/role/time_range/author 等）

### 2.3 向量与分块表（建议通用化）

#### 文档表（统一承载 resume / transcript / company-intel）
- `im_doc`
  - 关键字段：`doc_id`, `tenant_id`, `owner_type`（user/public）, `owner_id`（user_id 或 0）, `doc_type`（resume/transcript/company_intel/jd）, `source_ref`（file_url/url/session_id 等）, `language`, `status`, `created_at`

#### 分块表（可检索最小单元）
- `im_doc_chunk`
  - 关键字段：`chunk_id`, `doc_id`, `chunk_no`, `content`, `content_tokens`, `metadata_json`（公司、岗位、项目名、时间等）, `created_at`
  - 索引：`(tenant_id, owner_type, owner_id, doc_type)`, `(doc_id, chunk_no)`

#### 向量表（embedding 与 chunk 解耦，便于多模型并存）
- `im_chunk_embedding`
  - 关键字段：`embedding_id`, `chunk_id`, `embed_model`, `embed_dim`, `vector`（OceanBase 向量列类型/或兼容向量索引方案）, `created_at`
  - 索引：向量索引 + `(embed_model, doc_type, owner_type, owner_id)`

> 实操建议：把“用户私有向量空间”和“公共面经向量空间”在同表用 `owner_type/owner_id` 隔离；检索时强制拼接过滤条件，避免越权召回。

### 2.4 检索策略落地（多路召回）
- **语义检索**：向量 TopK（私有 resume/transcript + 公共 company_intel）
- **关键词检索（可选增强）**：对 `im_doc_chunk.content` 建全文索引/BM25（若 OceanBase 环境与能力允许；否则先用简单 LIKE/倒排服务替代）
- **重排（可选）**：引入 reranker（LLM 或轻量 cross-encoder）对 TopK 做二次排序，Phase 3+ 再做

## Phase 3：三条 RAG 流程设计（核心业务闭环，7-14 天）

### 3.1 RAG 链路 A：简历分析与押题（Resume-Based Q&A Prediction）

#### A1. 数据准备
- **输入**：PDF/Word 简历
- **处理**：解析 → 清洗 → 结构化抽取（技术栈/项目/指标/职责/空窗期）→ 分块 → embedding
- **产物**
  - `im_resume_fact`：结构化事实（用于“不可编造”约束）
  - `im_doc`/`im_doc_chunk`/`im_chunk_embedding`：用于语义召回（项目细节、描述段落等）

#### A2. 检索与生成
- **Query 构造**：按“岗位/方向/JD”生成多个子查询（技术栈、项目深挖点、风险点）
- **召回**：优先从用户私有 resume chunks 召回 TopK；必要时补充公共面经（同岗位）作为“面试风格”上下文
- **生成**：输出结构化题库
  - 每个项目：3-5 个由浅入深追问
  - 每题附：考察点、期望回答要点、追问分支

#### A3. 质量控制（MVP 必做）
- **Hallucination Check**：所有“引用项目事实”的句子必须可追溯到 chunk_id 或 `resume_fact`；否则降级为“建议性表达”并标注不确定性。

### 3.2 RAG 链路 B：全网面经检索与聚类（Company-Specific Intel）

#### B1. 数据摄取（Ingestion）
- **触发**：用户输入 company+role → 立即返回“缓存结果/历史结果”，同时异步刷新
- **外部检索**：Tavily Search 获取候选链接 → Firecrawl 抓取正文 → 清洗去噪（去导航/评论等）
- **分块策略**：按“题目/回答/段落”切分；保留 company/role/time_range/source_url 元数据
- **入库**：写入 `im_company_doc` + `im_doc*`（owner_type=public）

#### B2. 检索与聚类
- **召回**：按 company/role 过滤后向量检索 TopK，再按时间衰减加权（近半年更高权重）
- **聚类**：对 TopK 的问题片段做主题聚类（MVP 可用 LLM 做“主题归并”，正式版可换向量聚类）
- **输出**
  - 高频问题列表（带出现频率/来源数）
  - 面试风格画像（算法/八股/场景/系统设计占比）
  - 可持续更新（保存聚类结果版本）

### 3.3 RAG 链路 C：面试复盘批判与 Golden Answer（Interview Critique）

#### C1. 输入与预处理
- **输入**：transcript（问题-回答对）、resume、JD
- **结构化**：将 transcript 切分为 QA 单元；标注时间戳（如有）
- **召回上下文**
  - 从 resume 私有库召回与该问题相关的项目/技术细节 chunk
  - 从 company_intel 公共库召回同类问题高频要点（可选）
  - 从 JD 中抽取岗位关键能力（用于评分维度权重）

#### C2. 意图分析 → 评分 → 批判 → 优化（建议拆为 4 个子链）
- **IntentChain**：识别面试官问题在考察什么（深度/广度/沟通/权衡/边界条件）
- **ScoreChain**：按维度 0-100 输出（逻辑性、完整性、技术准确度、表达清晰度、贴合 JD）
- **CritiqueChain**：指出缺口（事实缺失、论证跳跃、概念不清、指标不自洽）
- **GoldenAnswerChain**：基于 resume 的可证据事实生成优化话术（STAR），并给出追问分支准备

#### C3. 报告产物（结构化为主）
- 每题：意图、评分、问题点、改进建议、Golden Answer、证据引用（chunk_id / fact_id）
- 全局：强弱项雷达、下一轮训练计划（推荐押题集与复习清单）

## Phase 4：LangChainGo 逻辑集成规范（可维护的 AI 编排，5-10 天）

### 4.1 统一封装层（建议在 `pkg/ai/`）
- **ModelClient**
  - 统一封装多模型调用（OpenAI/Claude/本地），支持超时、重试、熔断、降级
  - 输出必须支持“结构化 JSON + 解析校验”
- **EmbeddingClient**
  - 支持多 embedding 模型版本；写入 `im_chunk_embedding` 时记录 `embed_model/embed_dim`
- **Retriever**
  - `VectorRetriever`：OceanBase 向量检索 + 过滤条件（tenant/user/doc_type/company/role）
  - `HybridRetriever`：语义 + 关键词（后续增强）
- **PromptRegistry**
  - prompt 版本化：`prompt_key + version`；变更可追踪、可回滚

### 4.2 Chain 设计（按“可测试、可组合”拆小）
- **ResumeExtractChain**：简历 → JSON（facts）
- **ResumeRiskWeightChain**：facts → 风险点与权重
- **QuestionGenChain**：facts + role/jd + retrieved chunks → 押题集 JSON
- **InterviewIntentChain / ScoreChain / CritiqueChain / GoldenAnswerChain**

> 建议：每条 Chain 都定义输入输出 struct；并提供“离线回放测试”（给定固定输入与固定检索结果，输出可 snapshot）。

### 4.3 Tools 与 Memory（面向多轮对话与可控调用）
- **Tools（建议）**
  - `SearchCompanyIntelTool`：调用 `search-svc` 获取最新聚类摘要
  - `RetrieveResumeChunksTool`：按 query 从 resume 私有库召回
  - `RetrieveInterviewContextTool`：按 session_id 获取历史 QA、报告版本
- **Memory（建议）**
  - **短期记忆**：当前会话（session）最近 N 轮 QA 与偏好
  - **长期记忆**：用户偏好、常见弱项标签、学习计划（存入 `im_user_setting`/专用表）

## Phase 5：异步任务流（Asynq）设计（稳定吞吐与可重试，5-10 天）

### 5.1 典型耗时任务拆分

#### 任务 1：简历解析与入库（CPU/IO）
- **Job**：`resume.parse`
- **步骤**：下载文件 → 文本提取 → 清洗 → facts 抽取 → doc/chunk 写入 → enqueue embedding
- **幂等**：以 `resume_id + version + file_hash` 作为幂等键；重复提交只复用结果

#### 任务 2：Embedding 生成（外部调用/批量）
- **Job**：`embedding.generate`
- **步骤**：按 doc_id 拉取 chunks → 批量 embedding → 写入 `im_chunk_embedding`
- **策略**：批量、限流、失败重试（指数退避），记录失败 chunk 以便补偿

#### 任务 3：面经抓取与清洗（外部网络）
- **Job**：`company.ingest`
- **步骤**：搜索链接 → 抓取正文 → 去噪 → chunk → embedding → 聚类摘要（可分拆）

#### 任务 4：录音转文字（ASR）
- **Job**：`asr.transcribe`
- **步骤**：拉取音频 → 调用 ASR → 生成 transcript → 写入 doc/chunk → enqueue critique

#### 任务 5：深度批判复盘（LLM 长任务）
- **Job**：`interview.critique`
- **步骤**：按 session 拉取 QA → 对每题并发执行子链（intent/score/critique/golden）→ 汇总 → 写入 report
- **并发控制**：按 user_id 限流，防止单用户耗尽配额

### 5.2 队列与优先级建议
- `q.realtime`：用户触发且需要尽快返回的（轻量生成/小批 embedding）
- `q.batch`：面经抓取、批量 embedding
- `q.heavy`：深度批判、长文本总结

### 5.3 任务状态模型（建议统一）
- `im_task`：`task_id`, `type`, `ref_id`（resume_id/session_id/doc_id）, `status`（pending/running/succeeded/failed）, `progress`, `error`, `created_at`, `updated_at`
- API 返回 `task_id`，前端轮询或 WebSocket/SSE 推送（正式版）

## Phase 6：阶段性里程碑（Roadmap：MVP → Beta → 正式版）

### 6.1 MVP（对应需求 Phase 1：简历解析 + 押题，2-3 周）
- **必须交付**
  - 简历上传/解析/结构化 facts
  - 简历押题（每项目 3-5 题 + 考察点 + 追问分支）
  - OceanBase：元数据 + chunks + embeddings（至少私有简历向量库）
  - Asynq：resume.parse + embedding.generate
- **验收指标**

### 6.2 Beta（对应需求 Phase 2：面经检索 + RAG 融合，2-4 周）
- **必须交付**
  - company+role 面经抓取/入库/向量检索
  - 高频问题聚类与面试风格摘要
  - Resume 押题可融合“目标公司风格”上下文
- **验收指标**
  - 面经更新可用性（成功率/重复率/去噪质量）
  - 检索命中率与摘要一致性

### 6.3 正式版（对应需求 Phase 3：ASR + 复盘批判闭环，3-6 周）
- **必须交付**
  - 音频上传 → ASR → transcript 结构化
  - 逐题：意图分析、评分、批判、Golden Answer（带证据引用）
  - 复盘报告与训练计划（弱项标签 + 推荐题库）
  - 资源与成本治理（限流、熔断、配额、缓存、降级）
- **验收指标**
  - 端到端耗时（5-10 秒内返回“任务已受理 + 初步结果”，深度报告异步完成）
  - 报告一致性与可追溯性（引用 chunk_id/fact_id）

## 关键工程落地建议（贯穿所有 Phase）

### 1) 结构化输出优先
所有 AI 产物尽量输出为 JSON（评分、意图、问题点、golden answer、引用证据），业务端只做渲染与存档。

### 2) “不可编造”作为系统级约束
Resume/Interview 的生成必须带证据引用；当证据不足时明确输出不确定性与需要补充的信息。

### 3) 版本化与可回放
- Prompt、模型、embedding、chunking 策略都要可记录
- 关键链路支持离线回放（同输入、同检索结果）用于回归测试

### 4) 多租户检索防越权
检索层强制附加 `(tenant_id, owner_type, owner_id)` 过滤条件，避免向量召回跨用户泄漏。
